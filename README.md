# Паралельний пошук ключових слів у текстових файлах

Програма шукає задані ключові слова в текстових файлах і має дві версії:

- **threading**: багатопотокова обробка;
- **multiprocessing**: багатопроцесорна обробка з обміном даними через `Queue`.

Обидві версії повертають словник, де ключ — пошукове слово, а значення — список шляхів до файлів, у яких це слово знайдено:

```python
{'python': ['data/article_01.txt', 'data/article_02.txt', 'data/article_07.txt'], ...}
```

## Структура проєкту

| Файл | Призначення |
|------|-------------|
| `main.py` | Точка входу: запускає обидві версії, вимірює час і порівнює результати |
| `threading_search.py` | Багатопотокова версія (`threading.Thread` + `Lock`) |
| `multiprocessing_search.py` | Багатопроцесорна версія (`multiprocessing.Process` + `Queue`) |
| `search_utils.py` | Спільні функції: читання файлів, розподіл на частини, пошук, виведення |
| `data/` | Тестові `.txt` файли |

## Запуск

Потрібен Python 3.10+ без сторонніх бібліотек.

```bash
python3 main.py
python3 main.py --dir data --keywords python lock queue --workers 2
```

| Аргумент | Опис | За замовчуванням |
|----------|------|------------------|
| `--dir` | Директорія з `.txt` файлами | `data` |
| `--keywords` | Ключові слова для пошуку | `python thread process queue lock missing` |
| `--workers` | Кількість потоків/процесів | `4` |

## Як це працює

1. **Розподіл файлів.** Функція `split_into_chunks` ділить список файлів на `n` частин по колу, і кожна частина дістається окремому потоку або процесу.
2. **Пошук.** Кожен виконавець читає свої файли й шукає слова за регулярним виразом `\bслово\b` без урахування регістру, тобто тільки цілі слова (`lock` знаходиться в «Lock», але не в «block»).
3. **Збір результатів:**
   - у **threading** усі потоки мають спільну пам'ять, тому записують результати в один словник під `threading.Lock`, щоб уникнути race condition;
   - у **multiprocessing** кожен процес має власну пам'ять, тому надсилає результат у `multiprocessing.Queue`, а головний процес збирає дані з черги й об'єднує їх.
4. **Вимірювання часу.** Кожна версія вимірює час виконання за допомогою `time.perf_counter()`.

## Обробка помилок

- Файл не існує → `FileNotFoundError`
- Немає прав доступу → `PermissionError`
- Шлях вказує на директорію → `IsADirectoryError`
- Файл не в кодуванні UTF-8 → `UnicodeDecodeError`
- Інші помилки вводу-виводу → `OSError`

Помилкові файли записуються в лог і пропускаються, а решта файлів обробляється далі. Якщо директорії немає або в ній немає `.txt` файлів, програма завершується з кодом 1.

У multiprocessing-версії додатково:

- виняток усередині процесу передається через чергу як повідомлення про помилку;
- очікування результату обмежене тайм-аутом (30 с), тому програма не зависне, якщо процес аварійно завершився;
- після `join()` перевіряється `exitcode` кожного процесу;
- результати забираються з черги **до** виклику `join()`, щоб уникнути взаємного блокування (дедлоку).

## Висновки

1. **Обидві версії працюють коректно** і дають однаковий результат.
2. **Threading виявився значно швидшим** на цьому наборі даних (≈0.002 с проти ≈0.11 с). На 8 невеликих файлах запуск нових процесів (старт окремого інтерпретатора Python, імпорт модулів, серіалізація даних для `Queue`) займає більше часу, ніж сам пошук. Потоки створюються дешево й працюють у спільній пам'яті.
3. **Обмеження GIL** не дозволяє потокам виконувати Python-код справді паралельно, але для задач, де основний час іде на ввід-вивід (читання файлів, мережа), це майже не заважає: під час очікування диска GIL звільняється.
4. **Multiprocessing вигідний для CPU-bound задач** і великих обсягів даних: кожен процес має власний інтерпретатор і власний GIL, тому може повністю завантажити окреме ядро процесора. На тисячах великих файлів або при складній обробці тексту ця версія почне випереджати потокову.
5. **Практичний підсумок:** для пошуку в невеликій кількості файлів доцільно використовувати `threading`. Для важких обчислень над великими масивами даних краще підходить `multiprocessing`.
